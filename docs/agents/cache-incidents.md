# Superseded cache release incidents

Historical context only. The active policy is in `spec/agents.md`: CI owns both cache-marker files after merges. Do not follow the former PR-bump or conflict-number instructions below.

- **Historical policy — superseded; retained only for incident context:** Cache versions in `sw.js` were bumped by CI on the pull request, never by hand. The two caches moved independently so returning users re-downloaded only what changed:
  - `APP_CACHE_NAME` — `.github/workflows/sw-release.yml`, on a pull request touching `app.html`, `css/**`, `js/**`, `sw.js`, `manifest.webmanifest` or `tree-icon.svg` (the `APP_SHELL` contents). Note it watches `app.html`, not `index.html`: since the alpha URL split `index.html` is the marketing homepage and is deliberately not part of the app shell. It also syncs `APP_VERSION` in `js/app.js`, the fallback the About screen and bug reports show before `caches.keys()` resolves.
  - `DATA_CACHE_NAME` — `.github/workflows/data-bump.yml`, on a pull request touching `data/**`. That covers the Monday ledger merge and any regeneration script's output.

  Each sets its version to **one past the base branch's** rather than incrementing, so a pull request that triggers it twice lands on the same number. Both edit `sw.js` on the same branch, so they share a per-pull-request concurrency group rather than racing. The bump commit is pushed as `WEEKLY_LEDGER_PAT` (reused from `weekly-ledger.yml`), not the job's own `GITHUB_TOKEN` — a `GITHUB_TOKEN` push fires no new GitHub event, so the bump commit would become the pull request's head with no CI check ever run against it, which reads as green while actually untested. The PAT push is an ordinary user push, so it triggers a real `synchronize` event and `ci.yml` runs again against that exact commit. Expect **two** CI runs on any pull request touching these paths — the second one, on the bumped commit, is the one that actually gates the merge. No `[skip ci]`: the second run's own bump step finds nothing left to do and pushes nothing further, so this terminates rather than looping.

  **They used to run after the merge and push straight to `main`, and that broke silently when `main` became a protected branch** (`GH006: Protected branch update failed ... Changes must be made through a pull request`). Every merge from 19 September 2026 failed that way on a `push` event nobody watches, so the caches stopped being versioned while everything looked fine. Anything else that wants to write to `main` from CI has the same problem and needs the same treatment.

  A fork's pull request is skipped rather than failed: its token is read-only and its branch is not ours to write to, so a merge from a fork needs the bump by hand.

  **If a stale PR's `sw.js`/`js/app.js` conflicts with `main` on these version lines, don't hand-pick a number — take `main`'s side and push.** This happens when two or more qualifying PRs merge while a third sits unsynced: that third branch's bump was computed as "one past base" against a base that has since moved by more than one merge, so its line and `main`'s line now disagree and a merge can't auto-resolve them. Resolving by keeping `main`'s version (`git checkout --theirs sw.js js/app.js` during a local merge, or accepting the incoming change in GitHub's conflict editor) and pushing is always correct and sufficient: that push is a `synchronize` event, so `sw-release.yml`/`data-bump.yml` re-run and recompute "one past base" fresh against the current `main`, overwriting whatever was kept. There is nothing to merge by hand beyond clearing the conflict marker — the workflow redoes the arithmetic.
