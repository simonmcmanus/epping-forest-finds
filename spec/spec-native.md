# Native App Wrapper Specification (iOS / Android)

Ship Epping Forest Finds as a native app on the App Store and Google Play by wrapping the existing static client in a thin native shell, without rewriting the app or introducing a client build step for the web version.

The wrapper exists to buy things the mobile web cannot give a field navigation app: a location permission that is asked once and stays answered, a true-north heading that does not silently stall, a screen that stays awake while walking, and fully offline data from first launch. It is not a distribution trick — see [Store Submission Requirements](#store-submission-requirements).

## Detailed Specs

This spec owns everything inside `native/`, the `js/native.js` capability layer, the `native-cors` edge function, and the native branches of permission, heading, and data-resolution behaviour. Behaviour that is identical on web and native stays specified in its existing home:

- Every permission and consent ask, and the rules they share — [spec.md](spec.md) § Permissions and Consent
- Heading consumption, calibration gating, and staleness recovery — [spec.md](spec.md) § Compass and Direction Guidance
- Data loading and the `AppData` interface — [spec-data-fetching.md](spec-data-fetching.md)
- Drawing and interaction — [spec-data-rendering.md](spec-data-rendering.md)
- The closed alpha gate — [spec-alpha-access.md](spec-alpha-access.md)

## Chosen Approach: Capacitor

The client is vanilla HTML/CSS/JS with root-relative asset paths (`<base href="/">`), a 2D canvas renderer, and no bundler. Capacitor (8.x) loads exactly those files as local app assets in a native WebView (`WKWebView` on iOS, Android System WebView) and exposes native code through a plugin bridge; with no bundler, plugins are reached at `window.Capacitor.Plugins`. Nothing about the existing client has to change in order to render. Unknown paths fall back to `index.html` in both shells, so the app's own screen URLs (`/nearby/search`, `/settings`, …) survive a reload exactly as Netlify's rewrites make them do on the web.

Alternatives considered and rejected:

- **PWA install only.** Zero effort, but it cannot deliver the reasons this project exists: iOS gives no Screen Wake Lock, a `DeviceOrientationEvent.requestPermission()` grant that is re-prompted and lost across relaunches, and no store presence.
- **React Native / Flutter.** A full rewrite of a working, tuned canvas renderer. The rendering work in `js/renderer.js` and the tilt projection in particular are the product.
- **Tauri mobile.** Same shape as Capacitor but a far smaller mobile plugin ecosystem; no advantage here given the app ships no Rust.

Capacitor is reversible: the web deploy on Netlify stays the canonical build, and the native projects consume it. Deleting `native/` leaves the PWA untouched.

## Project Layout

```
native/
  package.json             # Capacitor CLI + plugins (native-only; never the web app's deps)
  capacitor.config.json    # appId uk.eppingforestfinds.app, webDir www
  www/                     # generated by scripts/sync-www.js (gitignored)
  ios/                     # Xcode project (Swift Package Manager, no CocoaPods), committed
  android/                 # Gradle project, committed
  resources/               # icon and launch-screen artwork (SVG sources + rendered PNGs)
  scripts/
    sync-www.js            # builds www/ from the repository by allowlist
    render-icons.js        # resources/*.svg -> the PNGs @capacitor/assets cuts icons from
js/native.js               # the only client file that knows about Capacitor
netlify/edge-functions/native-cors.js
```

`native/` holds its own `package.json` so the root project keeps its "no client build step, no external JS dependencies" constraint — Capacitor's dependencies are a native build-time concern and never a requirement for running the web app.

Everyday commands, from `native/`: `npm run sync` (rebuild `www/` and copy it into both projects), `npm run open:ios` / `npm run open:android`, and `npm run assets` after changing the artwork in `resources/`.

`scripts/sync-www.js` selects by **explicit allowlist** over the files git knows about (tracked, plus new files not ignored), never by copying the repository: `app.html` (written as `www/index.html`, the shell's entry), `terms.html`, `cookie-consent.js`, `manifest.webmanifest`, `tree-icon.svg`, `js/*.js` and `css/*.css` except the admin dashboard's, and `data/**` except source artwork (`data/icons/src/`), tracking logs and backups. A second list of paths that must never ship (`admin.html`, `js/admin.js`, `netlify/`, `server.js`, `scripts/`, `spec/`, `test/`, and the marketing `index.html`) is checked after selection, so a widened pattern fails the sync loudly. The allowlist is a security boundary, not a size optimisation.

The generated `ios/` and `android/` projects are committed because they carry hand-edited native configuration (permission strings, the privacy manifest, `AndroidManifest.xml`, orientation lock, icons) that `npx cap add` cannot regenerate. The web assets copied into them (`ios/App/App/public`, `android/app/src/main/assets/public`) are gitignored.

## Runtime Capability Layer (`js/native.js`)

Loaded first in `app.html`'s script order, before any request goes out. It exposes one global, `Native`, and nothing else in the client tests for Capacitor directly.

```
Native.isNative                  // true inside the shell (or under the test shim)
Native.platform                  // "ios" | "android" | "web"
Native.apiBase                   // "" on web; the site's origin inside the shell
Native.remoteUrl(url)            // what fetch() does to a URL (identity on web)
Native.geolocation               // navigator.geolocation on web; the native plugin, same callback API, in the shell
Native.locationPermissionState() // "granted" | "denied" | "prompt" | "unknown", from the Permissions API or the plugin
Native.compassNeedsPrompt        // false in the shell: there is no compass ask to make there
Native.unlockMotionOnFirstGesture(onGranted)
```

Every accessor is safe on the web and returns the web behaviour unchanged. `Native.isNative` is true when `window.Capacitor.isNativePlatform()` is, or when `window.__FORCE_NATIVE_SHIM__` is set (see [Testing](#testing)).

Planned additions, each landing with its phase: `heading` (phase 3), `keepAwake`, `haptics`, `share` (phase 4), `data` and `appVersion` (phase 5).

## Changes to the Existing Client

The full set of native-specific edits to shipped client code. Anything beyond this list is a sign the wrapper is leaking into the app and should be pushed back into `js/native.js`.

1. **`app.html`** — `<script src="js/native.js">` as the first script.
2. **Every location request** (`js/app.js`, `js/onboarding.js`) goes through `Native.geolocation`, with the same callbacks and the same `error.code === 1` for a refusal.
3. **API calls** — `js/native.js` wraps `fetch` inside the shell so a root-relative `/api/…` or `/.netlify/functions/…` URL goes to `Native.apiBase`. No call site changes; bundled files (`data/…`, `js/…`) still load locally. `NATIVE_API_BASE` at sync time points a build at another deployment (a deploy preview, a tunnel).
4. **Service worker** — never registered inside the shell (`setupPwa`, `js/nav.js`): a cache-first worker in front of bundled files would be a second, stale copy whose update prompt has nothing to wait on. Settings hides the web update line and the refresh buttons for the same reason.
5. **Compass** — `compassPermissionCanBeRequested()` is false in the shell, so the onboarding step reads "Your location" (no compass), the "Enable compass" card never shows, and the stored grant is never downgraded on launch.
6. **Sign-in** — hidden in the shell (Settings and Community). See [Not in the first release](#not-in-the-first-release).

Heading-up rotation, the radar cone, the calibration gate and the staleness watchdog run unchanged on WebKit's own `deviceorientation` events until the `forest-heading` plugin replaces the source (phase 3).

## Permissions Model

The point of the wrapper. The rules are the app's own and identical on every platform ([spec.md](spec.md) § Permissions and Consent): the app asks in its own words before any system dialog, an answer is remembered, location and usage analytics are separate questions, and a blocked permission is explained rather than re-asked. What is native-specific:

- **Location: one system dialog, never two.** `navigator.geolocation` inside `WKWebView` shows the app's own location prompt and then WebKit's per-origin "localhost would like to use your current location" prompt on top, every launch. Location therefore always goes through `@capacitor/geolocation` (via `Native.geolocation`), which asks once, through the OS, and is remembered by the OS.
- **Compass: no ask.** Capacitor's `WKWebView` delegate grants device-orientation access without a dialog; WebKit still only accepts `requestPermission()` from a tap, so `Native.unlockMotionOnFirstGesture` collects the grant silently on the first tap of a session and re-attaches the listeners. Android needs no permission for orientation.
- **Foreground only.** Nothing in the app records a walk, so there is no background location, no foreground service and no notification permission. They are added only together with a user-started walk-recording feature, never for analytics (see below).

### iOS (`ios/App/App/Info.plist`)

- `NSLocationWhenInUseUsageDescription` — "Shows where you are on the forest map and points you toward trees and places nearby."
- Portrait only. `ITSAppUsesNonExemptEncryption` false (HTTPS only).
- No `NSLocationAlways…`, no `UIBackgroundModes`, no `NSMotionUsageDescription` (WebKit's orientation events are not Core Motion activity data).

### Android (`android/app/src/main/AndroidManifest.xml`)

- `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `INTERNET`; `android.hardware.location.gps` declared not required.
- Portrait only.

### Hard constraint: background location is for the user, not for analytics

Both stores reject background location whose only beneficiary is the developer, and Play requires a written and video justification describing a user-facing feature. Background location may only ever serve a user-started walk recording whose result the user can see; usage analytics stays a separate, independently revocable, foreground-only consent.

## Native Heading Plugin (`forest-heading`) — phase 3

A first-party plugin, ~80 lines of Swift and ~80 of Kotlin. It exists because `webkitCompassHeading` is magnetic-north only, unsmoothed, and — as documented in [spec.md](spec.md) § Compass and Direction Guidance — stops firing on iOS and does not reliably resume.

- `available()` → `{ available }`; false without a magnetometer, so the client falls back to `deviceorientation` rather than to nothing.
- `start()` / `stop()`; stopped on app pause.
- `heading` event `{ trueHeading, magneticHeading, accuracy, timestamp }`; `trueHeading` is `-1` until a location fix exists, and the client uses `magneticHeading` until then.
- **iOS** — `CLLocationManager.startUpdatingHeading()`, `headingOrientation` kept in sync with the interface, `locationManagerShouldDisplayHeadingCalibration` returning `true`.
- **Android** — `TYPE_ROTATION_VECTOR` at `SENSOR_DELAY_GAME`, remapped for display rotation, declination-corrected with `GeomagneticField`.

The plugin replaces the heading *source*, not the pipeline: the existing smoothing, heading-up rotation, radar cone and tilt projection consume the same value. With a native source the staleness watchdog (`recoverStalledCompass`) returns early, and the calibration gate trusts a heading with good reported accuracy instead of waiting for agreeing samples, keeping `COMPASS_CALIBRATION_MAX_WAIT_MS` as the safety valve.

## Native UX

Built:

- **Orientation** — portrait only, matching `manifest.webmanifest`.
- **Icon and launch screen** — generated from `native/resources/` (the tree mark on the app's `#24382f`), full bleed for iOS, an adaptive icon for Android. The WebView background is the same green, so there is no white flash before first paint.
- **Android back button** — the WebView handles it, and the web router already gives it the right behaviour: back steps out of a selection, then out of Filters, and exits once the history is spent ([spec.md](spec.md) § URL / navigation state).

Planned (phase 4): keep-awake while navigating to a selected find (released on pause); a light haptic on arrival and on picking from the Nearby list, nothing else; the native share sheet for a selected find's URL; `env(safe-area-inset-*)` on interactive chrome with the status bar overlaid; rubber-band and pull-to-refresh disabled so they never steal a map drag; universal links / app links on the production domain (`apple-app-site-association`, `assetlinks.json` served by Netlify).

## Data Bundling

Every dataset ships inside the binary, so the app is fully offline on first launch with nothing to download except live cows.

- The sync strips whitespace from every JSON/GeoJSON file and rounds GeoJSON geometry to 6 decimal places (≈11cm); properties are never touched.
- `local-roads.geojson` and `local-environment-buildings.geojson`, opportunistic in the service worker, are bundled too.
- **Size (measured 27 Oct 2026):** 187 files, 58.1 MB on disk, about 9.5 MB compressed — well inside Apple's cellular download limit, so the fallback of leaving tree chunks out of the binary is not needed. Re-measure when a large dataset is added; the sync prints the total.

Until delta updates exist, the binary's data is as fresh as its release: the weekly data refresh reaches the web immediately and the app only at its next store release. That gap is accepted for the closed alpha and is what phase 5 closes.

### Delta Updates — phase 5

- A build step emits `data/manifest.json`: `{ dataVersion, generatedAt, files: { "<path>": { bytes, sha256 } } }`, published with the web build; the copy built at binary time ships as the baseline.
- On launch, online and at most once a day, the app fetches the live manifest, downloads only changed files into app storage via `@capacitor/filesystem`, verifies each `sha256`, and adopts each file atomically (temp name, verify, rename).
- `Native.data.resolve(path)` returns the downloaded copy when there is one and the bundled path otherwise — the single integration point in `js/loader.js`.
- Never blocks first paint; an update found on one launch is used on the next. Skipped on metered connections unless asked from Settings.

## Networking

- `Native.apiBase` is `https://www.eppingforestfinds.uk` unless the sync was given `NATIVE_API_BASE`.
- Requests from the shell are cross-origin (`capacitor://localhost` on iOS, `https://localhost` on Android). `netlify/edge-functions/native-cors.js` answers their preflight and adds `Access-Control-Allow-Origin` for those two origins only, on `/api/*` and `/.netlify/functions/report-missing-data`. Every other origin passes through untouched; credentials are never allowed; `/api/admin/*`, `/api/auth/*` and the community rebuild/validate endpoints are excluded in `netlify.toml`.
- Everything reached over the network already degrades offline (tracker queue, cached cows), and offline is the normal case in the shell.

## Not in the first release

- **Community sign-in.** It is a cookie session set by a redirect through the provider back to the website, which a page served from the bundle can never return from. Signed-out Community features work; points stay on the device. Doing it properly needs an in-app browser session and a token handed back by deep link.
- **Links to website-only pages** (the weekly ledger under `/reports/`, `/nearby/<slug>/` landing pages) resolve to the app inside the shell. Opening them in the system browser comes with deep links in phase 4.

## Versioning and the Update Story

The web build's cache markers and their bump workflow ([agents.md](agents.md) § Technical Constraints) are unaffected. Inside the shell there is no service worker, so the app code version is the store version (`CFBundleShortVersionString` / `versionName`), changed only by shipping a build. Settings → About shows the bundled app marker (`APP_CACHE_VERSION`) until `Native.appVersion` (phase 5) shows `v<store version> (data v<n>)`; bug reports carry the same value.

## Closed alpha

The alpha gate ([spec-alpha-access.md](spec-alpha-access.md)) guards the website's HTML. The app binary carries the app itself, so while the alpha is closed the binaries are distributed only through TestFlight and Play internal testing, never a public store listing.

## Testing

- **Unit** — `test/native.test.js` (in `npm test`): `js/native.js` executed against a fake Capacitor (web identity; API URLs sent to the site and bundled files kept local; the plugin behind the browser's callback API, including refusal vs time-out codes and clearing a watch; permission states; the silent first-tap motion grant); the sync's output (entry page is the app, nothing forbidden ships, every file `app.html` links and every dataset the service worker caches is present, geometry-only rounding); and the CORS edge function (both native origins, preflight never reaching the function, no grant for any other origin, no credentials).
- **BDD** — `test/e2e/40-native-shell.spec.js` runs the client's native branches under `__FORCE_NATIVE_SHIM__` with a fake Geolocation plugin: location only through the plugin, no service worker, no compass card, live data from the site's origin, no sign-in or web update controls. The ask rules themselves are covered on the web in `test/e2e/39-permission-asks.spec.js`.
- **Build** — `.github/workflows/native-build.yml` compiles both projects.

**Manual device checklist** — before each store submission, since nothing automated covers the native half:

- Fresh install in airplane mode: full map and tree data available.
- Exactly one system location dialog, and only after tapping the app's own "Enable location"; refusing leaves a usable map and is not asked again unprompted; Settings → Privacy → Use my location brings the dialog back while the OS still allows it, and explains where to turn it on once it does not.
- No compass dialog on iOS; heading-up works after the first tap; heading survives screen off/on and backgrounding.
- Usage analytics asked once, separately, after location; "No thanks" sends nothing (verify no `/api/track` requests).
- Android back button walks the screen history and exits at the end.
- Oldest supported OS on both platforms; one small and one tall screen (the tilt horizon is screen-height dependent).

## Store Submission Requirements

### Apple guideline 4.2 (minimum functionality)

A WebView wrapper with no native value is rejected under 4.2. The review notes must say concretely what the app does natively: fully offline datasets with no network requirement, OS-remembered while-in-use location, a live heading-up map, and — once phase 3 and 4 land — `CLLocationManager` true heading, wake lock during navigation, haptics and native share. The first submission should therefore wait for phase 3 at least, rather than submit the shell alone and add native value later.

Built: `ios/App/App/PrivacyInfo.xcprivacy` declares precise location, product interaction and a device id, each collected for analytics only, linked to the (random) device id, not used for tracking, and collected only after the in-app usage-analytics consent. Outstanding: App Store screenshots at every required size, age rating, and the privacy policy URL (`/terms.html`).

### Google Play

Data-safety form matching the same three data types. Play's prominent-disclosure rule is met by the app's own location step and invite, which always precede the system dialog. Target API level must meet the current Play requirement at submission.

### Both

- The admin dashboard is never in the binary (sync allowlist + forbidden list, asserted by `test/native.test.js`).
- A data-deletion path for the tracker's device id: today by email request ([terms.html](../terms.html) § 7); an in-app deletion action is needed before a public listing.

## Non-Goals

- No change to the web build's behaviour, dependencies, or "no client build step" constraint.
- No framework, bundler or TypeScript in the client.
- No native UI: every pixel stays in the canvas renderer and the existing DOM.
- No push notifications, no native map SDK, no raster tile downloads.
- No iPad or tablet layout work beyond not being broken.
