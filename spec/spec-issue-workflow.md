# GitHub Issue Clarification Workflow

- `.github/workflows/issue-clarify.yml` runs `anthropics/claude-code-action@v1` (authenticated via the `CLAUDE_CODE_OAUTH_TOKEN` repo secret, tied to a Claude Pro/Max subscription) on issue opened/edited and issue comment created/edited events. It replaced an earlier hand-rolled script that called the free GitHub Models inference API, which GitHub permanently retired on 2026-07-30.
- GitHub fires `issue_comment` for pull request comments too (PRs are issues under the hood), so the job also guards with `!github.event.issue.pull_request` to skip PR conversations entirely — this workflow's narrow "clarify, never write code" persona and its tool grant are wrong for PR threads. PR-side `@claude` requests are handled by the separate workflow below instead.
- Answers can be given either by editing the issue description or by replying in a comment — both retrigger the workflow.
- The action's own comment-reuse logic only applies to pull requests, not issues, so it always creates a brand-new tracking comment every run. **There is no cleanup step**: every run's comment is left in place, so the issue keeps its full history of question lists, answers, and confirmations across every run, not just the latest one.
- Tool grant: `mcp__github__update_issue` (rewrite the issue body/labels) plus read-only `Read`/`Grep`/`Glob` over this checkout, so a factual claim in a report (a place closed, moved, renamed, is mis-categorised) can be checked against the actual data files (`data/local-landmarks-food.geojson`, `data/local-landmarks-misc.geojson`, `data/business-watch.json`, `data/verification.json`) rather than taken on faith. No write access and no Bash — it can label an issue, but it never edits a file or opens a PR itself.
- The action reads `CLAUDE.md` and the `spec/*.md` files itself; the issue body and full comment thread (including its own prior comments, all still present) are already provided in context.
- As its first action, the workflow sets its (new) tracking comment to a plain "🤔 Thinking…" with no question list, since the previous run's statuses would be stale and confusing repeated under an in-progress indicator. It replaces the whole comment with the real content once done; the previous run's comment, if any, is left untouched above it.
- While questions remain open, the comment re-annotates the same numbered question list on each pass (same numbering/order/wording) with traffic-light status emojis (`🟢` answered, `🟡` partial, `🔴` unanswered) plus short answer-understanding blockquotes for answered/partial items; new follow-up questions are only appended, continuing the numbering, and only when genuinely needed.
- Once every question is 🟢, the workflow classifies the issue as a **bug** (clarified behaviour contradicts something already in the spec files) or a **feature request** (proposes behaviour the spec doesn't cover yet), independent of which template the issue originally used, then uses the `update_issue` tool to rewrite the issue body with the matching template's headings from `.github/ISSUE_TEMPLATE/` filled in with the clarified answers. If the classification differs from the original template, that's noted in the confirmation.
- It then decides whether the clarified, data-checked issue is a **simple, confirmed data correction** — one existing mapped place, a fact it could actually verify against the data, no design decision left. If so, it adds the `claude` label itself via `update_issue`, handing it straight to the Issue Agent Workflow below with no human labelling step, and says so in the confirmation ("🔧 Confirmed against the data — labelled for an automatic fix."). It never labels anything it couldn't confirm, or anything needing judgement — those stay for a person to label.
- It then posts a short confirmation instead of repeating the question list, followed by **Suggested spec update**: a hand-drafted unified diff (in a `diff` code block) against whichever `spec/*.md` file(s) an actual behaviour/UX/architecture change would touch, per the spec-sync convention in `CLAUDE.md`. This is a preview only — no file on disk is actually edited, no branch or commit is created. A pure data correction is never a spec change (see the root-cause rule in `spec/agents.md`'s Spec Synchronisation section) — the workflow says so explicitly, with the reason, instead of a diff.
- The job guards against re-triggering on its own comments/edits by skipping events where `sender.login` is `claude[bot]`. This workflow never implements anything or opens a PR itself — for a confirmed simple data correction it only applies the `claude` label; everything else needs a human to label it or otherwise act.
- The job has a 10-minute `timeout-minutes` so a hung run fails visibly instead of leaving the tracking comment stuck on "🤔 Thinking…" indefinitely — the next retrigger posts a fresh comment regardless.

## PR Assistant Workflow

- `.github/workflows/claude-pr.yml` runs `anthropics/claude-code-action@v1` (same `CLAUDE_CODE_OAUTH_TOKEN` secret) on `issue_comment: created`, gated to only pull request threads (`github.event.issue.pull_request`) containing `@claude`, and skipping the bot's own comments.
- No custom `prompt:` is set, so the action runs in its default tag-mode: it responds directly to whatever is asked in the triggering comment (implementing code changes, answering questions, etc.) rather than the issue-clarify workflow's fixed "grilling" persona.
- `permissions` grants `contents: write` and `pull-requests: write`/`issues: write` (PR comments are posted via the Issues API) so the action can commit and push to the PR branch and reply on the thread.
- `claude_args` extends the action's default tool grant with `Bash(git fetch:*)`, `Bash(git pull:*)`, and `Bash(git rebase:*)` so the session can reconcile with commits that landed on the branch after its initial checkout (e.g. from a concurrent run or a human push) before pushing, plus `Bash(node --test:*)`, `Bash(npm test:*)`, and `Bash(npm run test:*)` so it can run the unit suite before reporting a change as done. E2E (`npm run test:e2e`) is intentionally left out — it needs a Playwright browser install and is already covered by `ci.yml` on every push.
- Checkout uses `fetch-depth: 0` (full history) so `git rebase`/`git pull` against the branch's upstream has the commits it needs.

## Issue Agent Workflow

- `.github/workflows/claude-issue-agent.yml` runs `anthropics/claude-code-action@v1` (same `CLAUDE_CODE_OAUTH_TOKEN` secret) on `issues: labeled`, gated to the `claude` label so applying any other label doesn't trigger it. This is a self-hosted alternative to GitHub's native "assign to agent" issue panel — that panel's Claude connection authenticates through whatever credential is configured in the org/repo's Copilot-agent settings, not this repo's `CLAUDE_CODE_OAUTH_TOKEN`, so which subscription it bills against isn't visible from the repo. Labelling an issue `claude` instead guarantees the run uses this repo's own token. The label can come from a person, or from `issue-clarify.yml` itself once it has confirmed a simple data correction against the actual data — either way this workflow treats it the same.
- `label_trigger: "claude"` puts the action into its issue-implementation mode: it reads the (already-clarified, per `issue-clarify.yml`) issue body, implements the change, and pushes it to a new `claude/`-prefixed branch. Per the action's own documented limitation, this mode only prepares the branch and a prefilled compare link — it does not open the PR itself.
- Same `permissions` (`contents: write`, `pull-requests: write`, `issues: write`, `id-token: write`) and `claude_args` tool grant (`git fetch`/`pull`/`rebase` plus `node --test`/`npm test`/`npm run test`) as the PR assistant workflow, plus `Bash(python3:*)`: a data-correction issue (closed/renamed/mis-categorised place) is fixed by running the same scripts the weekly ledger uses (`apply_weekly_changeset.py`, `sync-homepage-counts.js`) rather than hand-editing a GeoJSON file, so the data stays internally consistent (homepage counts, verification records) the same way a weekly ledger change does. Unlike the PR assistant, this workflow runs `actions/setup-node@v5`, `npm ci`, and `npx playwright install --with-deps chromium` *before* invoking `claude-code-action` (mirroring `ci.yml`'s `e2e` job), so `npm run test:e2e` — already matched by the `npm run test:*` grant — actually has dependencies and browsers available when Claude runs it, rather than failing to bootstrap them itself (those setup commands aren't separately granted). This lets the agent run both suites before pushing, per the completion checklist in `CLAUDE.md`. Once the PR is open, further iteration happens there via `claude-pr.yml`, not back on the issue.
- A follow-up `Open pull request` step reads the action's `branch_name` output and opens the PR itself with `gh pr create` (title = issue title), skipping creation if a PR for that branch is already open. Issue title/number are passed through `env:` rather than interpolated into the `run:` script directly, since issue titles are attacker-controllable on a public repo and inlining them into a shell command would be a command-injection risk.
- Before diffing branches, the step clears any leftover `http.https://github.com/.extraheader` git config and re-fetches with an explicit `AUTHORIZATION: basic` header built from `GH_TOKEN`, scoped to that one `git fetch` via `-c`. The preceding `claude-code-action` step leaves behind its own scoped, push-only git credential (used to push the `claude/`-prefixed branch); a plain `git fetch` inherits that credential and fails authentication, since it isn't valid for fetch operations.
- The PR body reuses Claude's own commit message (already a proper summary/root-cause writeup, and it already contains `Fixes #<issue>` per the action's default commit convention) rather than a generic placeholder — it walks `origin/main..origin/<branch>` for the newest commit that isn't one of the automated `chore: bump/normalise SW cache version` commits landing on top, and falls back to a bare `Closes #<issue>` only if none is found or the message doesn't already reference the issue.
- The `claude` label itself (color `#6b46c1`) is created directly in the repo, not tracked in `.github/ISSUE_TEMPLATE/` — it exists purely as this workflow's trigger.
