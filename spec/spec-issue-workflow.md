# GitHub Issue Clarification Workflow

- `.github/workflows/issue-clarify.yml` runs `anthropics/claude-code-action@v1` (authenticated via the `CLAUDE_CODE_OAUTH_TOKEN` repo secret, tied to a Claude Pro/Max subscription) on issue opened/edited and issue comment created/edited events. It replaced an earlier hand-rolled script that called the free GitHub Models inference API, which GitHub permanently retired on 2026-07-30.
- Answers can be given either by editing the issue description or by replying in a comment — both retrigger the workflow.
- The action's own comment-reuse logic only applies to pull requests, not issues, so it always creates a brand-new tracking comment every run. A final workflow step (`Remove older tracking comments`, using `gh api` with `GITHUB_TOKEN`) deletes every earlier comment authored by `claude[bot]` on that issue except the newest, so **exactly one Claude comment is ever left on an issue at rest**, regardless of whether the run was triggered by an edit or a reply.
- The action reads `CLAUDE.md` and the `spec/*.md` files itself; the issue body and full comment thread (including its own previous tracking comment, before cleanup removes it) are already provided in context (Bash/`gh` access inside the Claude session itself is not needed or granted — the cleanup step runs as a separate, unsandboxed workflow step).
- As its first action, the workflow sets its (new) tracking comment to a plain "🤔 Thinking…" with no question list, since the previous run's statuses would be stale and confusing repeated under an in-progress indicator. It replaces the whole comment with the real content once done.
- While questions remain open, the comment re-annotates the same numbered question list on each pass (same numbering/order/wording) with traffic-light status emojis (`🟢` answered, `🟡` partial, `🔴` unanswered) plus short answer-understanding blockquotes for answered/partial items; new follow-up questions are only appended, continuing the numbering, and only when genuinely needed.
- Once every question is 🟢, the workflow classifies the issue as a **bug** (clarified behaviour contradicts something already in the spec files) or a **feature request** (proposes behaviour the spec doesn't cover yet), independent of which template the issue originally used, then uses the `update_issue` tool to rewrite the issue body with the matching template's headings from `.github/ISSUE_TEMPLATE/` filled in with the clarified answers. If the classification differs from the original template, that's noted in the confirmation. It then posts a short confirmation instead of repeating the question list.
- That confirmation also includes a **Suggested spec update**: a hand-drafted unified diff (in a `diff` code block) against whichever `spec/*.md` file(s) this change would touch, per the spec-sync convention in `CLAUDE.md`. This is a preview only — no file on disk is actually edited, no branch or commit is created. If no spec change would be needed, the workflow says so explicitly instead of a diff.
- The job guards against re-triggering on its own comments/edits by skipping events where `sender.login` is `claude[bot]`. There is no downstream agent that automatically implements the issue — clarification is the full extent of this workflow.
- The job has a 10-minute `timeout-minutes` so a hung run fails visibly (and the cleanup step still runs via `if: always()`) instead of leaving the tracking comment stuck on "🤔 Thinking…" indefinitely.
