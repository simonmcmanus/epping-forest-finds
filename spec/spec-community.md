# Community Verification (built: tree and place checks, add a missing tree or place, the Community screen with points, ranks, badges and streak, nudges, optional sign-in, rewards, admin tools and the City of London report; not built: the automated monthly export and a native-wrapper check, see Upstream loop)

## Public URLs
- **`/contribute`** (`contribute/index.html`, static, no app code): the plain-language explainer for walkers: how checks, points and ranks work and what happens to reports. Update it when the rules below change. Linked from the homepage and from the Community screen's summary card.
- **`/reports/tree-report`** (`netlify/functions/tree-report.js`, `lib/community-report-data.js`): the discrepancy report to share with the City of London, built from the same hourly snapshot as the overlay so it never shows more than the app does. Sections: trees questioned by two or more independent people (finding, number of people, last reported, listed and, for moved trees, reported position, with the register's tag and species looked up from the public tree chunks), possible new trees (tag number, position, one or more finders), conflicting reports, and a count of verified trees. Styled with the homepage's `assets/home/home.css` (hero with stat tiles, report cards, rows that stack as cards on a phone), no app code. Downloads: `?format=csv`, `?format=geojson`, `?format=json`; printable. Public and `noindex`; never contains device ids. Linked from the explainer and the admin Community panel.
- **`/community`**: the in-app Community screen (below). The nav tab stays labelled Community.

Lets users verify, question and add trees (and, with a different status set, businesses). Reports are an **annotation layer**; they never edit the shipped dataset.

## Source of truth
- The City of London dataset (`data/**`) is authoritative. Community reports never hide, move or delete a feature.
- A feature with enough agreeing reports shows a **"Questioned by the community"** badge in the inspector (with the reported status and count). Two independent reports that agree are enough to show it; the feature stays drawn as normal.
- Questioned features are exported for upstream (see Upstream loop). When a new City of London dataset lands, overlay entries it resolves are cleared by the reward check (`community-validate-scheduled`, daily).

## Architecture
- `netlify/functions/community-report.js`: validates, rate-limits, appends to a Netlify Blobs ledger. Idempotent on the client-generated report id.
- Hourly scheduled job (`community-rebuild-scheduled`): applies consensus and writes the snapshot `computed` (the overlay: target → `{s,st,n,t,...}`, plus conflicts) and per-device scores in 256 small shards (`scores/<2 hex>`); a request only ever reads the stored snapshot (an inline rebuild happens only if the snapshot is older than three TTLs, or on a non-production deploy). Conflicting reports about one tree are filed once as a GitHub issue (escalation only; not the store). The daily `community-validate-scheduled` job pays the rewards that depend on the register and on closed issues.
- `GET /api/community/overlay`: served outside `data/**`, so it never moves `data-cache-version.js`. The service worker caches it in its own `COMMUNITY_CACHE` with an independent version, stale-while-revalidate, ETag, refreshed hourly (edge-cached 5 minutes), fetched after first paint.

## Client
- **Built (phase 1):** `js/outbox.js` — IndexedDB outbox (in-memory fallback), items `{id,url,payload}` keyed by the report's `requestId` (server already de-duplicates on it). Flushes on `online`, `visibilitychange`, boot, and with backoff (5s/30s/2m/10m) after a network or 5xx/408/429 failure; other 4xx are dropped. Fires `outbox:change`/`outbox:sent` on `window`. Both feedback forms (Feedback screen and the per-location form) send via `sendOrQueueReport` (`js/app.js`): offline or unreachable → queued, status reads "Saved. It will be sent automatically when you're back online."; Submit is never disabled for being offline; the Feedback screen shows "N reports waiting to send". Cached in `APP_SHELL`.
- One offline **outbox** (reports and feedback), kept in IndexedDB; where that is unavailable the queue lives in memory and is mirrored to `localStorage` (`ff-outbox-fallback-v1`, small payloads only, so a photo does not fit) so a reload does not lose it. If even that fails (`outboxIsDurable()` is false) the report form says it will only send while the app stays open, and the Community screen shows a note above the log. Flushed on `online`, `visibilitychange`, app start and Background Sync where available; exponential backoff; "N waiting to send" chip.
- **Optimistic UI**: a submitted report is merged over the feature locally at once, with the note "Saved. Other people may take an hour or two to see this." The local copy is dropped when the hourly overlay includes it.
- Anonymous device identity: a random 24-character id kept on the device, which is the whole credential (there is no separate secret), with a recovery code that is the same id. Optional sign-in adds an account that groups devices (see Accounts).

## Visual design
All community UI uses the inspector's existing vocabulary (white cards, 1px hairlines, 10-12px radius, `--tree` green, `--gold-tint` for attention) and the nav's 2px round line icons (`communityIcon`, `COMMUNITY_ICONS` in `js/community.js`, `currentColor`, 24px grid). Rules:
- **Placement and boxing:** on a tree's detail screen the check block sits directly above the Nearest section (places put it in the same spot, see Place checks) (after the tree's own details), and is a single tinted, bordered card (`.community-check`) holding the header, the verify action, a "Something not right?" divider and the choices, so the choices read as part of the check.
- **Tree check block:** header (shield icon, "Help check this tree", "Is it where the map says it is?"), one full-width primary action (verify) that carries the points chip for what it earns now (`+1`, or `+0` outside the zone or without location, kept live by `communityUpdateRangeNotes`), then a **"Something not right?"** disclosure button (`communityMoreHtml`, 44px, chevron turns when open) that unfolds a two-column grid of icon chips (≥44px targets, labels wrap). The grid is folded at rest and open while changing an earlier answer or once the walker has opened it (`data-more` on the section survives re-renders). After a report the choices are replaced by a success card (check, "You reported: …", "Thank you! Other people may take an hour or two to see this.", the points chip rising in (static under reduced motion), a **Change** link that brings the choices back with the current one marked). A questioned tree shows an amber alert card, a verified one a green shield card, above the actions.
- **Contributions card (Community screen):** rank icon + name + points and points to next rank, a progress bar, three stat tiles (Verified, Confirmed by others, Your reports), then one card per report: status icon, tree name (links to the tree), status text and an outcome pill with its own icon (*Waiting to send* upload, *Awaiting a second opinion* clock, *Confirmed by others* check, *Being reviewed* alert). With no reports, an empty state with the app's tree illustration explains how points work.
- **Add a missing tree (Community):** a card with the tree illustration and a **Start** button that opens the boxed form (live GPS status row, tag number, optional note, Cancel / Submit tree).
- **Reward vocabulary and tokens:** `:root` carries the community tokens (`--c-radius` 14px, `--c-radius-sm` 10px, `--c-hairline`, `--c-lift`, and the reward gold `--c-reward*`), used for community cards instead of one-off radii. The **rank medal** (`communityMedalHtml`) is a 56px CSS medal with a ring and face per rank (Seedling, Sapling, Woodward, Warden) holding the rank icon; it replaces the flat tile in the rank card. The **points chip** (`communityPointsChipHtml`, `communityPointsChipFor`) is a gold "+N" pill ("up to +2" for a "not right" check, a grey "+0" outside the zone or without location) shown before the points line; gold is used only for rewards.
- Motion is a 260 ms fade/rise on the success card and a width transition on the progress bar; both are disabled under `prefers-reduced-motion`.
- The score read back from storage is always coerced to numbers; a malformed response can never print "undefined".

## The Community screen
The nav tab formerly called **Feedback** is now **Community** (people icon), at **`/community`** (a gated app screen like `/settings`; `/contribute` is the public explainer, below). The tab keeps its element id `#reportToggle`. **Feedback** is its own page at `/feedback` (so published links and `/feedback#report=<text>` still open the form), reached from a "Send feedback" link at the bottom of the Community screen; the Community tab stays lit on it, and tapping the tab there returns to Community. The Community sheet opens taller than other screens on phones (`.inspector-tall`, 78% by default, applied without a transition so the map camera fits the sheet's real footprint, set in `syncHashFromSelection`; a height the user has dragged to wins) because it is all content and has no use for a big map. The screen is, top to bottom:
A cold load of `/community` opens this screen at the very start of `boot()`, before map data or location arrive (it needs neither), and the boot reveal skips `selectOverview()`/`applySelectionFromHash()` while it is open (and `applyLocationFix` leaves it selected), so the Nearby list and the nudge card never show over it first. The early call waits one microtask because `boot()` starts before the rest of `app.js` has initialised its constants.
0. **Summary row**: "Help keep the map right" with a "How it works" link (new tab) to the explainer `/contribute` (`communityIntroHtml`).
1. **Hero** (`#communityContributions`, `communityRenderContributions`): a card with the rank medal, rank name, points and points to the next rank, a 12px progress bar (`aria-valuetext` names the rank), the three counts (Verified, Confirmed by others, Your reports) as one divided row, and the **streak** with a seven-day strip (`communityWeekDays`: the last seven days, today last, a tick on each day with a report). The section keeps a visually hidden "Your contributions" heading.
2. **Sign-in** (`#communityAccount`): signed out it is a slim banner ("Keep your points on any device") with a dismiss button; once dismissed (`ff-community-signin-dismissed-v1`) it becomes a single quiet link. Signed in it shows the name and Sign out.
3. **Do something now** (`communityActionsHtml`): "Check trees near you" (links to Nearby; the line under it asks for location when it is off), then **Add a missing tree** and **Add a missing place** (below).
4. **Badges** (`#communityBadgesHost`, `communityBadgesHtml`): a header with the count ("4 of 7") and a horizontal scroller of medal tiles. An earned badge has a gold-rimmed medal and "Earned"; a locked one a grey medal, a progress bar and "have/goal" (`communityBadgeProgress`, capped at the goal). Tapping a tile opens, in place under the scroller, how to earn it and the walker's progress (`communityShowBadgeDetail`); tapping again closes it. Each badge in `COMMUNITY_BADGES` carries its `metric`, `goal` and `how`.
5. **Your reports** (`#communityLog`): the map-mark legend, a filter (All, Needs attention (N), Confirmed; shown from three reports) and the log, newest first except that *Couldn't send*, *Waiting to send* and *Being reviewed* rows are pinned to the top. Each row is one line: icon, name, status and relative date (`communityRelativeDay`: Today, Yesterday, N days ago, then a short date) and the outcome pill, which wraps beneath on a narrow row. Outcomes are *Waiting to send* (still in the outbox), *Awaiting a second opinion*, *Confirmed by others*, *Being reviewed* (conflict) or, for place changes, *Sent for review* (with a "View on GitHub" link once the issue exists). Tree and place names are links: a tree opens its page, and a place opens its own `/find/<slug>/` page, the slug being stored with the report; an older entry without a slug opens on the map as `/nearby#place=id:…`; coordinate-only places stay plain text. The log is built from the local record so it works offline; outcomes come from `GET /api/community/overlay?me=<id>&list=1` (a per-device `mine/<deviceId>` index written by `community-report.js`, `reportOutcome` in the consensus module), cached in `ff-community-log-v1`. Whenever the hero is replaced by a note (loading, identity check failed) the badges and log are emptied too, so a previous person's rows never show. Settings no longer carries this section.
6. **Add a missing place** (`communityAddPlaceHtml`): a form with the place's name, a type (pub, café, restaurant, shop, toilets, car park, visitor attraction, other) and an optional note; its position is the user's own GPS fix (accurate to 30 m or better, as for trees). It is filed as a `place-check` issue with status `NEW_PLACE` and the key `new:<lat 5dp>,<lon 5dp>` (so a repeat from the same spot joins the open issue), labelled `place:new:…`. A person reviews every one; nothing is added to the map automatically. The log shows "Reported a missing place" with a "Sent for review" pill and the GitHub link.
7. **Back up or restore**, the nudge setting and **Send feedback** (a link card to the Feedback page, the existing form, unchanged).

### Add a missing tree
A form, never a one-tap action: **Start** reveals the form; nothing is saved or logged until **Submit tree**.
- **Tag number is required** (it identifies a new tree). "0" and empty tags are refused (thousands of untagged register entries carry 0). A tag already in the dataset is refused with "already on the map" so the user checks that tree instead.
- **Location must be close and accurate:** the tree's position is the user's own GPS fix, which must have a reported accuracy of 30 m or better. A live status row shows *Using your location · accurate to N m* or what to do (turn location on, step into the open). Submit stays disabled until a tag is entered and the fix is good enough. The server enforces the same rules (`validateReport`: tag number present, `accuracy` ≤ 30 m).
- Two people reporting the same tag number are the same new tree (matched by tag, not position); a second person makes it `new-confirmed`. Optional free-text note.

## Place checks (pubs, cafes, shops and other places)
A boxed **Help check this place** card sits on a place's detail screen **above** its Nearest/Related sections (not on events), so it is seen before the walker scrolls away. Its one-tap action is *Yes, it's still here and correct*; the other choices are behind the same "Something not right?" disclosure as a tree's. Choices: *Yes, it's still here and correct*, *It's closed*, *It has moved*, *The name has changed*, *Details are wrong*, *Wrong type of place*.
- A **confirmation** is a local-only check-in: it scores nothing, never opens an issue, and hides that place's check card on this device.
- Any **change** opens a short note step (required for rename and wrong details, optional otherwise) and is filed as a **GitHub issue for manual review** via `report-missing-data` (`reportType: "place-check"`, labels `place-check` + `user-report` + a per-place label `place:<id>` such as `place:node/123`, so one place's issues can be listed with a label filter). Nothing is applied to the data or shown to other users automatically; a person decides. A further report about the same place (matched by a `place-key:` marker) is added as a comment on its open issue instead of a new issue. Requests carry the usual de-duplicating request id and travel through the offline outbox.
- No community overlay or "questioned" badge exists for places.
- **Issues raised on the place:** under the place's card, a line appears only when GitHub has `place-check` issues carrying that place's `place-key:` marker. It reads "The community has raised N issues about this place (N still open / all closed)" with a **See them on GitHub** link to the repo's issues filtered by `label:place-check` and that marker, open and closed. It is filled in after the place renders (`loadCommunityPlaceIssues`, `js/community.js`; a public search, no token), cached per session, and stays hidden on any failure or when there are none. It is live GitHub data, so the static `/find/<slug>/` page cannot include it.

## When the server refuses a report
The outbox never strands a late addition: a flush requested while one is already running is remembered and run again as soon as the first finishes (`outboxFlushAgain`, `js/outbox.js`).

The outbox drops a report the server refused with a 4xx (other than 408/429) because retrying cannot fix it. For every queued report type (tree reports to `/api/community/report`, and place changes and feedback to `report-missing-data`) the app records the server's message on the local entry (`failed`, plus the payload to retry) from the `outbox:sent` event when `ok` is false. The log row then shows a **Couldn't send** pill, the reason, and a **Send again** link (`communityRetry`) that puts the same request back on the outbox (same request id, so it is never filed twice). It never claims "Sent for review" for a report the server rejected.

## Reporting from too far away
Anyone can report on a tree from anywhere. The tree check card carries a range card (`communityRangeNoteHtml`, `js/community.js`) that follows GPS fixes, with a heading, a body and a points line (`communityPointsText`): inside the 10 m check zone ("Inside the 10 m check zone", points "+1 now, +1 more if someone else confirms", or "up to +2 if others agree" for a "not right" choice); outside it ("Outside the 10 m check zone", "Points: 0 from this check"); or with no location ("Location is off", "Points need your location"). The card is compact (one heading line, one body line, the points chip) with a left accent in each state. A report made from too far away is stored with `far: true` locally, its success card shows the same points line ("Points: 0 from this check") next to "It only earns points when you report within 10 m of the tree", and its log row shows the `far` pill until the server says otherwise. The points match `netlify/functions/lib/community-points.js`; the card shows what the check earns, not the total. Place checks have no distance rule. Adding a missing tree separately requires an accurate fix (30 m or better) and cannot be submitted without one.

## Recovery code
The anonymous device id is the whole identity, so the Community screen has a collapsed **Back up or restore your progress** card: it shows the id in groups of four (`communityRecoveryCode`) with a Copy button and warns that anyone with the code can act as you. **Restore** accepts the code as shown or any case, spacing or dashes (`communityParseRecoveryCode`: exactly 24 letters and digits once those are stripped, lowercased), fetches that id's reports from `?me=<id>&list=1`, adopts them into the local log, switches the device id, clears the cached score and log, and refreshes. Online only; a malformed code is refused with a message. Possession of the code is the proof, as before; a signed-in account (below) is the alternative that needs no code.

## Nudges
With a real, accurate fix (30 m or better) and a tree within 10 m that this device has not yet checked, the app prompts once per tree per day (`communityNudgeCheck`, `js/community.js`, called with every GPS fix). On the Nearby overview it shows a dismissible card ("You're next to tree N", a "+1" chip, **Check it** and a close button, auto-dismissed after 20 s) and at most one such card every 10 minutes. If that tree's own page is already open there is no card: the check card pulses twice (a static outline under `prefers-reduced-motion`). Users can turn nudges off with a checkbox on the Community screen (`ff-community-nudges-off-v1`). Nothing is shown for the stand-in location or inaccurate fixes. Constants are at the top of the Nudges block in `js/community.js`.

## Accounts (sign-in)
The public privacy and terms page (`/terms.html`, section 13) describes this to users: what a report holds, that place changes and feedback become public GitHub issues without the device id, the Auth0 sign-in, the `ff_session` cookie, what an account stores, and how to ask for deletion by email. It must be updated with any change to what is stored, and the retention and deletion wording is a commitment that needs the owner's (and any legal) review before sign-in is enabled.
Optional. Points work without signing in. Signing in lets one person's devices share a score and log.
- **Provider:** Auth0 (OpenID Connect, hosted login page). Social and email providers are switched on in the Auth0 dashboard, not in code. The app has no client SDK: the Community screen's **Sign in** is a plain link to `/api/auth/login?return=/community`.
- **Functions:** `auth-login` (redirect to the provider with a signed, 10-minute `state` cookie), `auth-callback` (exchanges the code on the server, reads `/userinfo`, sets the session), `auth-me` (`{signedIn, name, account}`, where `account` is the one-way account hash, never the provider id), `auth-link` (POST `{deviceId}`, adds the device to the account), `auth-logout` (clears the session). Routes are in `netlify.toml`. `/api/*` is outside the alpha gate.
- **Session:** an HttpOnly, Secure, SameSite=Lax cookie `ff_session`, HMAC-signed with `AUTH_SECRET`, valid 30 days. It holds only the provider's subject id and a display name. An email address is never used as a name and never stored. No session store.
- **Accounts:** `devicelink/<deviceId>` = `{account}` is the one authoritative record of who owns a device; membership is one marker record per device, `accountdevices/<account>/<deviceId>`, so two links never read-modify-write a shared list. The account key is a hash of the provider subject. A device belongs to one account; linking it to another returns 409 and the Community screen says so (see *Shared browsers* below). An account holds at most 20 devices (a soft cap: concurrent first links can overshoot it by a few). Linking claims the owner record first, re-reads it to see whether a concurrent link won, then writes the marker; a failure in between leaves the device owned but not yet a member, and linking again completes it. Every read (`devicesForRequest`) checks each marker against the owner record, so a stray or stale marker never exposes another account's device.
- **One account is one voice:** when the snapshot is built (`rebuildComputed`) the owner records are read (`loadDeviceOwners`, `lib/community-links.js`) and devices of one account count as a single reporter in consensus (`latestPerDevice`), in the confirmed-by-others and second-finder bonuses, and in the reporting allowance (`a:<account>` scope in `lib/report-rate-limit.js`), so linking more devices adds no votes and no capacity. Anonymous devices remain separate voices. Scores are still per device and add up under the account.
- **Scores and log:** `?me=<deviceId>` (and `&list=1`) reads every device of the signed-in account when the requested device is one of them, and sums scores (`mergeScores`) or merges the logs newest first. Reports, consensus and the ledger are unchanged; nothing is moved.
- **Client:** `communityRefreshAccount` (`js/community.js`) reads `/api/auth/me` (`{signedIn, name, account}`, where `account` is the same one-way hash used server-side), links this device when the stored marker (`ff-community-linked-v1` = `<deviceId>|<account>`) is not this device and this account, and renders the card `#communityAccount` above the contributions list. The marker is per account: signing out clears it, and a different account on the same browser links the device again. The card shows the name and a **Sign out** link when signed in.
- **Shared browsers (account isolation):** every read and write on the client goes through the active device id (`communityDeviceId`): the signed-in account's own device id on this browser (`ff-community-account-devices-v1`, `{account hash: device id}`), otherwise the browser's primary id. Local history, score, log and score timestamp are stored per device (`communityScoped`: the primary id keeps the original keys, any other id gets `<key>:<deviceId>`). When an account signs in and linking the primary id answers 409 (it already belongs to another account), the client mints a new device id for that account, links it, and says "you're starting fresh here"; that account sees none of the other account's local history or score, and reports it makes are filed under its own id. Signing back in as the first account restores its id and history; signed out, the browser is the primary id again. On the server (`devicesForRequest`) a signed-in account that does not own the requested device is never given it: it gets only its own devices (an unowned device is read alone until it is linked; an anonymous caller still gets the device alone, as before).
- **Away from the forest:** on the Community screen, a user whose real location is outside the map area (`state.userInMapArea` false) is not shown on the map and the camera does not follow them. It frames every mark they have made (`fitCommunityOwnMarks`; the whole forest when they have none). While this holds, `nearbyNavigationAnchorActive()` is false, so there is no heading-up anchoring on a point far off the map. Someone at the forest gets the existing Nearby-style framing (walking radius plus their marks). Marks that arrive after the screen opened (another device's history merged by `communityRefreshLog`) trigger a redraw and, for someone away, a refit (`communityMarksChanged`).
- **Identity before history:** the contributions area is not drawn from storage until `/api/auth/me` has answered (`communityOpenContributions` awaits `communityRefreshAccount`, 6 s bound), so a second person on a shared browser never sees the previous account's rows, name or score for a moment. The same holds when the screen is opened again on a page that already drew it: the account card and list are reset to a neutral "Loading…" before the wait. Until the first answer on a page, no request that names a device (score, log) is sent either (`communityWhenIdentityKnown`), so a previous account's id never goes out while someone else signs in. A failed answer (error, timeout) does not count as one: while a signed-in account is remembered and the check fails, those requests stay unsent and the screen shows the "couldn't check" note; the next call tries `/api/auth/me` again. Offline, the last known account stands. If the network is up but the answer fails and a signed-in account is remembered, no history is shown, only "Couldn't check who is signed in just now"; an anonymous browser carries on as normal. The account and the per-account device map are also held in memory (`communityAccountMemory`, `communityAccountDevicesMemory`): where storage is blocked or full, the id stays stable for the life of the page and the account card says this browser can't save the sign-in, so history made on it won't be remembered after the page closes (a reload mints a new id for that account).
- **Look and tests:** the sign-in card (`.community-account-card`) holds the text, the button and any note together (green-tinted Sign in / Sign out button, gold note). Three mobile visual snapshots protect it, `test/e2e/35-community-snapshots.spec.js` (signed out, signed in with history from other devices, device already linked to another account); like every baseline they are written by CI, never by hand. They are mobile-only on purpose: the app is a phone-first field tool and every other app-screen snapshot is mobile-only, so desktop gets the functional specs (`33`, `34`) but no pixel baseline.
- **History across devices:** the log merges the reports the server returns for the account (`communityMergeRemoteReports`) into the local log, keeping only well-formed fields. A report still waiting to send, a failed one, or a local one that is as new or newer is never replaced; server entries are marked `remote` and `counted` (already in the server score, so never added again as optimistic points or streak days). When the signed-in account changes or the visitor signs out, every `remote` entry and the cached outcomes are removed, so one person's history is never shown to the next person on the same browser.
- **Cookies:** the session and state cookies are `HttpOnly`, `SameSite=Lax` and `Secure` whenever the request came in over https; over plain http (local development on localhost, which `baseUrl()` treats as http) `Secure` is left off, because the browser would never send a Secure cookie back and sign-in could not complete (`isSecureRequest`).
- **No durable storage:** if the browser cannot keep the Community id, `communityDeviceId()` keeps the first id it made for the life of the page, so one session is not split across identities, and the recovery card says the code is not saved (`communityDeviceIdIsDurable`).
- **Configuration (Netlify env vars, per deploy context):** `AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, `AUTH_SECRET` (32+ characters). Unset, the auth endpoints answer 503 and the card still offers sign-in, which fails gracefully. Auth0 needs `https://<site>/api/auth/callback` as an allowed callback URL for each origin used, including deploy previews and, for `npm run dev`, `http://localhost:8080/api/auth/callback`. `server.js` serves the same auth routes locally (the env vars are read from the shell).
- **Sign-in and sign-out links** (`/api/auth/*`) are full page loads. The in-app link handler (`js/nav.js`) skips `/api/` paths, so the browser follows them to the provider and back, never into an app screen.
- **Known limits:** the device id is the proof when linking, so anyone holding a device's id can link it to their own account (same trust as the recovery code). Signing out does not end the provider's session in the browser, so signing in again can be automatic. Two simultaneous links for one device can race: one wins the owner record and the other can never read it (tested).

## Tree statuses
`VERIFIED`, `NO_TAG_LIKELY_SAME`, `NO_TAG_UNSURE`, `DIFFERENT_TREE`, `NOT_HERE`, `MOVED` (carries a dragged pin position), `NEW_TREE` (GPS position, optional tag/species). Businesses: `OPEN_CONFIRMED`, `CLOSED`, `MOVED`, `RENAMED`, `DETAILS_CHANGED`, `WRONG_CATEGORY`, `NEW_PLACE`. Statuses live in a registry keyed by feature kind.

## Consensus (as implemented)
Latest report per device per target. A report only counts (points and consensus) when the reporter's own position was within 10 m of the tree (`NEAR_METRES`, `lib/community-points.js`); a report from further away, or with no position at all, is still saved and shown to the reporter but scores nothing and does not count towards "questioned"/"verified". Its log row says "Not close enough for points" (outcome `far`). ≥2 independent devices agreeing on a question status (and outnumbering confirms) = `questioned`; confirms with no questions = `verified` (≥2 = `confirmed`); confirms and questions together = conflict, held for review and not shown. `NEW_TREE` reports match on an ~11 m grid; a second device makes `new-confirmed`.

(Original design notes:)
Independent devices only. Verify + independent verify = confirmed. Two agreeing change reports = "questioned". Conflicts, and `NEW_TREE` without a second sighting, escalate to an issue. Reports within ~40 m of the feature are trusted fully; others are flagged and score less.

## Scoring
All values and rank thresholds are configured in `netlify/functions/lib/community-points.js` and explained in `docs/community-points.md`.
+1 on verify, +1 when independently confirmed. `NEW_TREE` +1, +3 when found by a second device. Accepted correction +2. Points show as pending until the server accepts them. 
**Rewards after the fact** (`REWARD_POINTS` in `lib/community-consensus.js`): +10 when a later City of London register validates a report (a reported new tree's tag now exists, a "not here" tree is gone, a moved tree's register position changed towards the report; `lib/community-validation.js`), +1 when a feedback or bug issue is closed as completed, +3 when a place-check issue is closed as completed. The first validation run only records a baseline, so existing differences never pay out, and only reports made at or before the previous run (the last time the old register was still seen unchanged) can earn it: the register changed somewhere between the previous run and this one, so anyone who waits for an update and then posts what it says falls after that cutoff. Reporters are matched through an HMAC `reporter-ref` stored in the issue; the device id is never in the issue. A daily scheduled function (`community-validate-scheduled`) and an admin `/api/community/validate` run the check, idempotently. Place confirmations earn nothing.

**Badges and streaks** (`communityBadges`, `communityStreaks`, `js/community.js`) show under the rank card: earned badges lit, the rest dashed, plus a day streak. They are derived on the device from the (optimistic) score and the local log, award no points, and need no server (see the Community screen for how they are shown). Quests and area progress are follow-ups. Leaderboard is private in v1.

### Trees added by walkers on the map
Entries `new:tree:*` in the shared overlay (a walker's added tree, `new` or `new-confirmed`) are drawn as blue plus marks (`communityOverlayNewTreeMarks`, `drawCommunityMarks`) on every screen except Community, which shows only the user's own reports. They disappear when the register gains the tag (validation drops the overlay entry). Tapping one opens its page (`#addedtree=<tag>`, `showAddedTreeDetails`): tag, how many walkers found it, "Not on the City of London register yet", the distance and an Open in Maps link, and an "I found it" button that opens the Community add-a-tree form with the tag filled in (a second sighting confirms it). The tap wins over cluster-free pins under it; a cluster badge over the same ground still takes the tap first. The route needs the overlay, so on a cold load of an `#addedtree=` link `boot()` waits for the overlay (`communityEnsureOverlay`, up to 4 s) before resolving it; if the overlay never arrives the link falls back to Nearby.

### Optimistic score
Points and the verified count shown on the Community screen are the server's score plus what the device has earned that the server cannot have seen yet (`communityPendingScore`, `js/community.js`): a verify (+verify point, +1 verified) and a new tree (+new-tree point) from a report made near the tree. Corrections, second opinions, far reports, refused reports, reports adopted from the server on restore (already in its score), places and feedback add nothing until the server scores them. The score response carries `generatedAt`; a local report stops counting once a score with `generatedAt` ≥ its timestamp arrives, but keeps counting while it is still in the outbox. `COMMUNITY_POINTS` mirrors the server config (unit-tested).

### Conflict escalation
A tree whose near reports both confirm and question it is a conflict: no result is shown. The hourly rebuild (`community-rebuild-scheduled`, and the admin `/api/community/rebuild` on the production deploy only) files each new conflict once as a GitHub issue titled `Community conflict: tree <record>`, labelled `community-conflict`, `user-report` and `tree:<record>`, with the report counts, a link to the tree and its listed position (`lib/community-escalation.js`). What has been filed is kept in the store (`escalations`), so a tree is never filed twice; at most 10 per run, failures are retried next run, and without a GitHub token nothing is filed. Previews never file issues.

### Hardening of the report ledger
`validateReport` refuses report ids and device ids that are JavaScript object-key names (`__proto__`, `constructor`, `prototype`), kinds and statuses that are not own properties of the status registry, and targets that are not `tree:` or `place:` keys with no whitespace. The snapshot maps keyed by those values (`overlay`, `scores`, the score shards) are null-prototype objects, so a hostile id can never reach `Object.prototype`. A contributor's own outcome for a new tree is looked up under its canonical key (`canonicalTarget`: `new:tree:tag:<tag>`, since a new tree has no `target`), so a register reward shows as *validated* and a second finder as *confirmed*.

### Abuse protection on issue creation
The public endpoint that files GitHub issues (`report-missing-data`: place checks, missing places, feedback) caps reports per hour so nobody can drive unlimited issues from the server's token: per client IP (Netlify's `x-nf-client-connection-ip`, not anything the caller sends), per device id, and one site-wide cap (defaults 20 / 10 / 300, overridable with `REPORT_LIMIT_PER_IP`, `REPORT_LIMIT_PER_DEVICE`, `REPORT_LIMIT_GLOBAL`). Counts live in one small hourly store document (`lib/report-rate-limit.js`); over a cap the answer is 429 with `Retry-After`, which the outbox treats as retryable, so the report is kept and sent later. The counts are not atomic, so a burst can overshoot slightly, and if the store is unreachable the report is let through rather than lost. The community-report endpoint (`/api/community/report`) has the same kind of brake in its own hourly document, because a caller-chosen device id cannot prove a second report is a second person: per IP, per device and site-wide (defaults 120 / 120 / 5000, `COMMUNITY_LIMIT_PER_IP`, `COMMUNITY_LIMIT_PER_DEVICE`, `COMMUNITY_LIMIT_GLOBAL`), 429 with `Retry-After` when exceeded; a repeat of an accepted report is answered as a duplicate before it is counted. This slows minting of fresh ids but is not a full defence: consensus only annotates a tree (it never changes the register), and points that matter (the +10 reward) are paid only after the City of London's own register agrees. The per-place `place:<id>` label is created before the issue (GitHub silently drops labels it does not know); an existing label (422) or a failure there never blocks the report.

## Scaling
- The snapshot (overlay, conflicts, score shards) is rebuilt **hourly** by `community-rebuild-scheduled` (`COMMUNITY_TTL_MINUTES`, default 60); in production a request serves a snapshot up to 3 TTLs old rather than rebuild inline, and rebuilds itself only if the schedule has stopped. Previews and local dev rebuild on request after the TTL (scheduled functions do not run there).
- To force a rebuild while testing, use **Rebuild snapshot now** on the admin Community panel (`/api/community/rebuild`, admin password); it also runs at the end of every reward check.
- The public overlay is cached 5 minutes in browsers and at Netlify's edge (`Netlify-CDN-Cache-Control`, with stale-while-revalidate), so request cost does not grow with the number of users.
- "My score" reads one of 256 small shard blobs (`scores/<xx>`). The app keeps the score on the device and only re-asks the server when it is over an hour old, after a send, or when the Community screen opens.
- Others' reports therefore show up roughly an hour after being made, plus up to the cache time; the reporter sees their own immediately. If the report volume reaches tens of thousands, move the ledger to a database.

## Upstream loop
The questioned/confirmed discrepancies are available as CSV and GeoJSON downloads on `/reports/tree-report` (feature id, status, count, last reported, position) to send to the City of London so they can issue a corrected dataset. **Not built:** an automated monthly export that produces and sends it. After a new dataset is ingested, the daily reward check clears resolved overlay entries.

## Data deletion
On a privacy request the owner runs `POST /api/community/delete` (admin, `Bearer ADMIN_PASSWORD`; body `{deviceId, confirm: "delete", includeAccount?, redactIssues?}`; `lib/community-delete.js`). It removes the device's reports, `mine/` index, the uncapped per-issue records (`issues/<deviceId>/<number>`, written when a place change or feedback issue is filed, so the 300-entry `mine/` cap can never hide an issue from a deletion), `devicelink/`, account membership markers, per-day counters, reporter references, reward records and score-shard entry, with the account's other devices too when `includeAccount` is set, then rebuilds the snapshot so the overlay and scores no longer include them. Public GitHub issues filed from the person's place changes and feedback are redacted and closed only when `redactIssues` is set, on the production deploy, with a token; otherwise their numbers come back as `pending` for a person to handle. Every read that decides what is deleted (lists, reports, `mine/`, links, refs, rewards, score shards, and the closing rebuild) is strict in both store implementations (`getStrict`; a missing file is "nothing there", an unreadable one is a failure). A storage failure while listing or reading stops the deletion with a 503 (never `deleted: true` over leftovers), and the request is simply sent again. Deleting twice is harmless; a bad device id, a missing password, a non-POST or a missing `confirm` is refused. The Auth0 user, usage tracking, Google Analytics and the mailing list are outside it. The procedure is `docs/community-data-deletion.md`; the retention wording on the privacy page remains the owner's decision.
